Gemma 4 E2B 在 Hexagon NPU 上的推理验证

llama.cpp_hui @ 4b0773c7d，对比上游 aa588a346 · 模型 gemma-4-E2B-it-qat-Q4_0.gguf（3.35 GB，35 层，sha256 fa401b55…）
设备 SM8845（本地 OnePlus PLR110）、SM8850（QDC Canoe 开发机）· 2026-10-31

E2B 在两台设备上都能正确运行，但这版优化没有让它变快。这些优化主要面向 Qwen 和 MoE 大模型，在 E2B 上大多没有进入执行路径。

NPU 的优势集中在提示处理：SM8850 的 pp512 为 2,229 t/s，是 CPU 的 9.6 倍。生成速度上 NPU 为 36.5 t/s，略低于 6 线程 CPU 的 38.0 t/s。

测试还发现一个问题：SM8845 部分卸载时，如果 NPU 轮询和 CPU 线程池轮询同时开启（run.py 原默认配置），6 线程生成速度跌到约 1 t/s。关闭任一轮询可恢复，run.py 的默认配置已修复。

后续提速实验（只在 SM8845 上做，见“优化细节和提升倍数”）：用现有的批量解码，24 路并发的总吞吐可达单路的 10 倍以上，但每一路会变慢。单路生成做不到 10 倍，最好的是大量照抄输入的任务，约 5.7 倍；普通问答没有提速。

主要结论

  1. 优化前后无可测提升。SM8850 上 pp512 -0.2%、tg64 +0.0%，内存相同，相同参数下输出文本一致。
  2. NPU 适合处理长提示，也能腾出 CPU。生成阶段 NPU 不比 CPU 快，但不占用 6 个 CPU 核心，host 线程数对它几乎没有影响。功耗没有测量，能效优势还不能下结论。
  3. 矩阵乘法占 NPU 时间约 89%。其中输出层 lm_head（Q6_K，词表 262144）单项约占 19%，是后续优化最值得先看的地方。
  4. SM8850 的 NPU 明显更快。两者都是 HTP v81，SM8850 的 pp512 比 SM8845 高 43%，tg64 高 30%。但 SM8845 测试时 CPU 被限频，机型也不同，这个差距不能全部归因于芯片。
  5. 10 倍只在多路总吞吐上成立。单路生成每个词元都要读约 1.38 GB 权重，瓶颈很可能是内存带宽；批量解码可以共用一次读取，所以总吞吐能大幅提升。
  6. 批量大小会改变 NPU 的输出，但没有发现数据损坏迹象。NPU 按批量大小切换计算路径，数值结果略有差异，两个候选词接近打平时输出就可能不同。

优化细节和提升倍数

下表汇总本次所有优化手段。倍数只在“对比基准”一列的条件下成立，不能相乘，也不能当作同一个“整体提速”。

优化做法对比基准提升代价或条件
fork 原有优化（流式、预取、专家缓存等）面向大模型的内存和 IO 优化，详见下节。上游基线，全部层在 NPU，SM8850tg64 1.00 倍，pp512 1.00 倍对 E2B 基本无效；大模型未测
轮询配置修复部分卸载时 run.py 默认关闭 NPU 轮询。修复前默认配置，SM8845，16 层 NPU，6 线程tg64 约 18 倍（1.0 到 17.6 t/s）是修复异常，不是超出正常水平的提速；SM8850 未复测，也未出现这个问题
多路批量解码（24 路）多个请求合成一批，共用一次权重读取。单路 tg，SM8845总吞吐 10.7 倍（10.2–11.5）每路变慢；未模拟真实请求
多路批量解码（32 路）同上。单路 tg，SM8845总吞吐 12.9 倍（12.2–13.6）每路更慢；未模拟真实请求
单路推测解码（n=4，m=32）从输入中找重复片段，批量验证猜测。不推测，代码改写，SM88455.7 倍（31.1 到 178.2 t/s）只对大量照抄输入的任务有效；输出可能和单步不逐字相同
单路推测解码（n=2，m=16）同上。不推测，SM8845，单次运行普通问答 0.9 倍 / 代码评审 1.6 倍 / 代码改写 2.9 倍普通问答反而略慢
使用 NPU 代替 CPU把提示处理放到 NPU。这是后端选择，不是本次新增的优化。CPU 6 线程，SM8850pp512 9.6 倍，tg64 0.96 倍生成阶段不比 CPU 快；功耗未测

10 倍目标的结论：多路总吞吐已达到，单路生成没有达到。普通问答的单路速度仍约 30 t/s。要明显提高单路速度，需要减少每个词元读取的权重，例如换用更小的模型或更低比特量化，这部分没有测试。

优化方案和原理

相对上游，fork 新增约 2500 行代码。下表按代码路径判断每项优化能否作用于 Gemma 4 E2B（Q4_0、稠密 FFN、模型能完整放进内存）。

优化原理开关对 E2B
权重流式用 O_DIRECT 按层读取留在 host 的权重，放进两块轮换缓冲区：当前层计算时预读下一层，用顺序读取替代缺页。LLAMA_WEIGHT_STREAM不生效。只接入 qwen35 图；开启后日志也没有 streaming 记录
层预取计算某层前，提前把后续层的 mmap 页读入页缓存，减少推理线程阻塞在缺页上。LLAMA_LAYER_PREFETCH不生效。同样只接入 qwen35 图
专家预取MoE 模型按路由结果只预读会用到的专家权重，并预测下一层的专家。LLAMA_EXPERT_PREFETCH不适用。E2B 不是 MoE
专家缓存把常用专家权重留在一块固定内存里，避免反复从闪存读取。LLAMA_EXPERT_CACHE_MB不适用
块稀疏 FFN把 FFN 权重按块稀疏化，由 gguf_ffn_blockify.py 转换模型，减少需要读取和计算的权重。LLAMA_FFN_SPARSE_BLOCKS不适用。需要转换模型，且只在 qwen35 图中实现
IQ 量化 tiled 矩阵乘把 IQ4/IQ3/IQ2/IQ1 重排成 HMX/HVX 可直接处理的 tile，由查表还原权重，让这些量化在 NPU 上运行。随权重类型自动启用不适用。E2B 是 Q4_0，上游已支持
大批量 NPU 卸载留在 host 的层遇到不少于 32 行的矩阵乘时，把权重复制到计算缓冲区，运行时重排后交给 NPU。GGML_HEXAGON_OFFLOAD，默认 32路径可能触及，但开关前后无差异，原因未确认
mmap 预取策略模型超过一半内存时不再整体预取，避免加载阶段把整个模型读进来。LLAMA_MMAP_PREFETCH不触发。E2B 小于内存的一半
rpcmem 预算分配 NPU 内存前预留可用内存（默认 2048 MiB），放不下时报错，避免 rpcmem 占满内存拖垮手机。GGML_HEXAGON_MEM_RESERVE生效但不影响速度。手机旧日志显示 E2B 曾因此报错退出；本次未做内存压力测试

这些优化在大模型上的效果本次没有测试，上面的结果不能说明它们没有价值。要评估它们，需要用 Qwen 或 MoE 模型另做一轮。

测试方法

  • 两个构建：优化版是 fork 提交 4b0773c7d，基线是它合并的上游提交 aa588a346，用同一工具链容器交叉编译。
  • 两类负载：llama-bench 测 pp128、pp512、tg64；llama-completion 用固定提示、temp 0、seed 1 跑端到端生成，并检查输出文本。
  • 轮次交错：各用例按轮交替运行，减少温度漂移造成的偏差。主要对比项 5 轮，其他 3 轮。表中为中位数，小字是最小到最大值。
  • 运行状态：SM8845 每次运行前唤醒屏幕并等待 Thermal Status 回到 0（最多等 15 分钟），通过 Wi-Fi adb 控制且 USB 线仍连着。SM8850 通过 SSH 隧道控制，无需亮屏。功耗模式默认 high_performance，NPU 轮询开启（GGML_HEXAGON_OPPOLL=1，与 run.py 一致）。少数运行等待超时后 Thermal Status 仍为 1。
  • 样本量：SM8845 为 71 次有效运行和 15 次轮询实验。SM8850 第二次会话为 71 次运行和 18 次冷启动，第一次会话 56 次用于复现性核对。没有运行失败。

如何读这些数据

下面说明报告中各项数据测的是什么，以及读数时要注意什么。

速度

数据含义怎么看
t/s每秒处理的词元（token）数。词元是模型处理文本的单位，一个词元可能是一个词或词的一部分。越高越好。
pp128、pp512提示处理（prompt processing）速度：模型一次读入 128 或 512 个词元时的速度。决定长提示要等多久。例如 2000 t/s 读完 512 个词元约需 0.26 秒。
tg64文本生成（text generation）速度：逐个生成 64 个词元时的速度。决定回答出字有多快。它和 pp 相差很大，不能互相换算。
端到端生成 t/s用真实提示运行 llama-completion 时的生成速度。比 tg64 更接近实际使用。不同设备的输出长度可能不同，不宜跨设备直接比较。
11 词元提示耗时读入一段 11 个词元的短提示所用的时间。反映短问题的首字等待，不含模型加载。
模型加载 ms从启动到模型可用的时间。受页缓存影响很大；冷启动一节是清空缓存后的结果。

配置

数据含义怎么看
NPU、GPU、CPU分别由 Hexagon HTP、Adreno（OpenCL）、CPU 核心执行计算。比较速度时，也要考虑是否占用其他资源。
全部层、部分卸载（-ngl）-ngl 指定放到加速器上的层数。全部层是整个模型都在 NPU 上，16 层则其余部分留在 CPU 上。部分卸载要在 CPU 和 NPU 之间来回协作，所以结果和全部层差别很大。
host 线程数CPU 上参与计算和调度的线程数。全部层在 NPU 上时影响很小；部分卸载时影响很大。
NPU 轮询、CPU 轮询等待任务时持续检查（响应快但占 CPU），而不是休眠等待。两者同时开启，是 SM8845 部分卸载时速度崩溃的触发条件。
high_performance、balancedNPU 的功耗模式。这里只比较了速度，功耗差异没有测量。
上游基线、优化版上游 aa588a346 和 fork 4b0773c7d。用来判断 fork 的改动是否带来变化。

统计和系统状态

数据含义怎么看
大数字和小字范围大数字是多次运行的中位数，小字是最小到最大值。范围重叠时，差异通常不足以说明谁更快。
变化 %优化版相对上游基线的变化。要结合波动范围判断，几个百分点的差异可能只是波动。
RSS进程占用的物理内存峰值。不等于总内存占用：NPU 另有内存记在设备上，且部分重叠。
峰值 °C运行期间所有 CPU 温度传感器的最大值。只用于相对比较，开发机的读数不代表手机表面温度。
Thermal Status、频率上限系统报告的热状态和 CPU 允许的最高频率。SM8845 状态为 0 时 CPU 仍被限频，它的 CPU 数据低于芯片能力。
算子占比各类计算占 NPU 时间的比例。用来找优化重点。开启剖析后整体会变慢，所以只看比例，不看绝对时间。

提速实验

数据含义怎么看
总吞吐所有并发路每秒生成的词元数之和。代表系统能力，不代表单个用户感受到的速度。
每路速度总吞吐除以路数。这才是每个用户看到的出字速度。
一步耗时处理一批词元的时间，每路各生成一个词元。路数增加时涨得越慢，批量的收益越大。
倍数同一轮内，多路总吞吐除以单路 tg。10 倍的目标看这个数。
推测解码、n、m先按输入中出现过的片段猜接下来的词元，再一次批量验证。n 是匹配长度，m 是每次最多猜几个。猜中才会提速；猜错会浪费计算，可能比不推测更慢。
草稿数、接受数、接受率猜了多少词元、验证通过多少，以及两者之比。接受率低但总速度高也是可能的，最终以 t/s 为准。

数值一致性

数据含义怎么看
logits模型给词表中每个词元打的分，分数最高的词元在贪心采样时被选中。比较 logits 比比较文本灵敏，文本相同不代表计算结果相同。
逐位相同、不同比例两次计算的 logits 是否完全相等，以及不相等的比例。100% 不同也可能只是很小的数值差异，要结合 rms 看。
rms所有 logits 差异的均方根，表示典型差异大小。越小越接近。
最大绝对差所有 logits 中最大的单项差异。它受少数极端值影响，只说明最坏情况。
最高分翻转分数最高的词元变了多少次。翻转才会直接改变贪心输出。
最小领先差第一名和第二名分差的最小值。分差越小，数值差异越容易改变输出。

ggml-hexagon 库本身默认不开 NPU 轮询（opt_oppoll = 0），但 scripts/snapdragon/run.py 默认设置 GGML_HEXAGON_OPPOLL=1，手机上已有的 bench.sh 和本次矩阵也都开启了它。所以用这些脚本测部分卸载会遇到崩溃，不设这个变量的程序则不会。

run.py 的修复

已修改 scripts/snapdragon/run.py（本地提交 3ab067605）：检测到部分卸载（-ngl 小于 99，或 -ot、--cpu-moe 等）时，NPU 轮询默认为 0；全 NPU 时仍为 1；--hex-oppoll 可显式覆盖。没有全局关闭，因为全 NPU 下轮询是取舍关系：SM8845 交替运行 5 轮，开启时 tg64 中位数 30.5 t/s、pp512 1542 t/s，关闭时 28.4 t/s、1725 t/s。

通过 run.py 在 SM8845 上验证（16 层 NPU、6 线程）：默认配置下 tg64 为 15.2、17.6、19.6 t/s；显式 --hex-oppoll 1 时 1.0 t/s，崩溃可复现；全 NPU 仍为轮询开启。SM8850 未复测这项修改。手机上的 bench.sh 写死了 OPPOLL=1，不受这项修改影响；上文的部分卸载表格是修复前的数据。

目标是把推理速度提高 10 倍。这部分全部使用现有功能和参数，没有修改推理框架源码。配置为全部层在 NPU、2 线程、NPU 轮询开启。

瓶颈分析

固定路径的速度代价很大，也没有完全解决问题：代码评审提示的输出仍然不同。它从约 1576 词元开始生成，途中会跨过 1792 这个 KV 对齐边界。此外，CPU 上位置跨过 256 后，单步和批量的 logits 也开始不同（最大约 0.57），关闭图复用后不变。这可能和 KV 按 256 对齐有关，根因没有查明。

建议：日常保持默认配置，不要为了可复现而切到固定路径。批量解码的结果可以视为与单步等效，但不是逐位相同。需要逐字复现时，使用单路、不开推测，并固定配置和提示。

建议的下一步

  1. 验证真实并发。用 llama-server 多槽位和不同长度的请求测吞吐与延迟，并在 SM8850 上重复提速实验。
  2. 查清 256 边界的差异。它在 CPU 上也出现，不限于 NPU。
  3. 优化 lm_head。它占约 19% 的 NPU 时间。可以试更低比特的量化，或复查 Q6_K 大矩阵的 NPU 路径，再评估精度影响。预期收益还只是估算。
  4. 给 Gemma 4 接入流式和层预取。只有模型超出可用内存时才有意义。E2B 不需要，12B 这类模型可能需要；手机上已有的 12B 测试脚本也只尝试部分卸载。
  5. 另做一轮大模型验证。用 Qwen 或 MoE 模型，在内存压力下对比这些优化，这才是它们的目标场景。
  6. 补上功耗测量。NPU 和 CPU 的生成速度接近，选择哪个主要取决于能效，而这次没有这项数据。

数据限制

SM8845 的 CPU 全程受限。即使 Thermal Status 为 0，CPU 上限大多仍只有约 2266/1651 MHz（硬件最高 3322/3802 MHz）。CPU 和部分卸载的数据明显低于芯片能力；NPU 全层的结果受影响较小但也不是满血数据。SM8845 的纯 CPU pp128 还出现 12–149 t/s 的双峰，原因未查明。

SM8845 第一轮数据已弃用。第一轮在息屏 Doze 状态下运行，没有用于上表，保留在 results/full/sm8845-throttled-doze.jsonl。

没有测试 Gen 6。本次云端设备是 SM8850，不是你最终要调试的 Gen 6 芯片。

两次 SM8850 会话用了不同设备。序列号分别是 64a112da 和 cf39e6a。结果高度一致（opt_htp pp512 2,239.5 对 2,229.3，tg64 36.3 对 36.5），表中使用第二次的数据。开发机与量产手机的散热和存储不同。

不同设备或后端的输出不完全相同。同一设备上优化版和基线文本一致，但 SM8845 NPU（56 词元）与 SM8850 NPU 和 CPU（66 词元）不同，SM8845 CPU 则与后者一致。两份回答都合理；这可能来自数值差异，尚未查明，所以端到端生成速度不宜跨设备直接比较。批量大小对输出的影响见“批量解码的数值差异”一节。

提速和数值实验范围有限。都只在 SM8845 上做，SM8850 没有测；部分结果是单次运行，已在表中注明。CPU 受限频影响，这里的倍数不能直接套用到其他设备。
